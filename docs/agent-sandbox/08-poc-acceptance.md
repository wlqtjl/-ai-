# 08 · POC 验收指标与自动化校验

> 对应计划「可立即产出 · 第 8 项」，落实报告 18.5「预先定义可量化的成功判据」。
> 自动化检查：[`tools/poc_gate.py`](tools/poc_gate.py)　指标模板：[`templates/poc-metrics.template.json`](templates/poc-metrics.template.json)
> **第二轮复核修订**：删除全部**不可证明**的指标，改为可证明的表述。对照表见第 2.1 节。

## 0. 本文依赖的假设

| 假设 | 类型 | 若不成立 |
| --- | --- | --- |
| [A1/A2](00-assumptions.md) 数据通路可支撑目标并发 | **假设（A2 有反证）** | 效率与规模类目标值必须下调 |
| [C3](00-assumptions.md) 客户接受脱敏 + 变更导出的组合 | **假设** | 指标表需按合并路线重写 |

## 1. 规则

1. 指标在 POC **启动前**与客户共同确认并冻结，事后不得调整口径；
2. 分两档：**红线指标（redline）** 任一不达标即 POC 判负；**目标指标（target）** 不达标记为待改进；
3. 结论由脚本产出，不由人主观判断（避免用「客户觉得不错」结题）；
4. **每个指标必须可证明**：写不出「用什么证据、如何全量或统计地判定」的指标，
   一律不许进指标表。抽样得到的结论只能表述为**区间或上界**，不得表述为「= 100%」。

## 2. 指标表

| 维度 | 指标 | 档位 | 目标值 | 说明 |
| --- | --- | --- | --- | --- |
| 安全 | 源端新增权限/挂载/代理数量 | **红线** | = 0 | 对应第七部分设计红线，破坏即失去核心优势 |
| 准确性 | fixture 全集失配数 | **红线** | = 0 | **全量可判定**，不是抽样；用 `compare_changesets.py` 判定 |
| 可靠 | **非预期**的生产库写入次数 | **红线** | = 0 | 首版不写生产库，因此任何一条写入都属非预期；判定方式见证据字段 |
| 方法 | SLA 目标是否由实测反推 | **红线** | = true | 防止再次出现「先写漂亮数字再想办法达成」|
| 合规 | 交付沙盒中脱敏默认开启的比例 | **红线** | = 100% | 与风险 R5 的定性一致，第一轮误列为目标档 |
| 安全 | Agent 成功自审自批的次数 | **红线** | = 0 | 权限模型有效性的直接验证 |
| 安全 | 到期未回收的沙盒数（含孤儿资源） | **红线** | = 0 | 资源泄漏与凭据残留 |
| 效率 | `near_current` 创建耗时 P95 | 目标 | **待阶段 0 实测反推** | 第一轮写死 < 5 分钟，比白皮书唯一的最优单例（6 分钟）还激进 |
| 效率 | 端到端耗时较现有人工流程降幅 | 目标 | ≥ 80% | 与客户共同测定基线 |
| 规模 | 单集群并发存活沙盒上限 | 目标 | **待阶段 0 实测反推**（第一轮写 ≥ 100）| 20 MB/s 的实测通路与 100 并发差约 50 倍，见 02 文档第 7 节 |
| 效率 | 创建耗时预估准确度 | 目标 | 误差 ≤ 50% | SLA 承诺可信度 |
| 可靠 | 变更集导出成功率 | 目标 | ≥ 99% | 排除因冲突被正常拒绝的情况 |
| 准确性 | 生产负载失配率 95% 上界 | 目标 | ≤ 0.1% | 由观测失配数与比对行数推导（rule of three / Wilson），**不得手填** |
| 隔离 | 备份/容灾任务耗时劣化 | 目标 | ≤ 5% | 验证队列隔离（06 文档） |
| 成本 | 每 GB 写入的存储放大倍数 | 目标 | ≤ 2.0 | COW 增量取决于写入量，不是相对全量克隆的固定比例 |

### 2.1 第一轮 → 第二轮的指标改写对照

| 第一轮指标 | 问题 | 改为 |
| --- | --- | --- |
| ChangeSet 一致率 = 100% | **抽样在数学上无法证明总体 100%**，却被做成 `== 1.0` 的浮点判定，把不严谨包装成了严谨 | ① fixture 全集零失配（全量可判定，红线）② 生产负载失配率 95% 上界（目标）|
| 生产库受影响次数 = 0 | 「受影响」未定义——若做合并，写生产本来就是预期行为 | **非预期**生产库写入 = 0，并定义可观测的判定方式（生产库审计日志中来自沙盒服务账号的写操作）|
| 单沙盒存储 ≤ 全量克隆 5% | COW 增量取决于写入量，不是固定比例，分母选得不对 | 每 GB 写入的存储放大倍数 ≤ 2.0 |
| 脱敏开启率（目标档）| 与风险 R5「合规红线」的定性自相矛盾 | 升为**红线**（首版选择脱敏 + 变更导出路线的直接结论）|
| P95 < 5 分钟 / 并发 ≥ 100 | 目标值拍脑袋，比唯一的最优实测值还激进 | 由阶段 0 实测反推，并新增「SLA 目标由实测反推」这条红线做制度化约束 |

## 3. 使用方式

```bash
# 1. 复制模板，POC 期间由测试脚本或人工填入实测值
cp templates/poc-metrics.template.json /tmp/poc-run-01.json

# 2. 产出判定结论
python3 tools/poc_gate.py /tmp/poc-run-01.json

# 3. 回归自测（内置通过/红线失败/目标未达三种样本）
python3 tools/poc_gate.py --self-test
```

退出码：`0` 通过；`1` 红线不达标（POC 判负）；`3` 红线通过但存在目标未达（有条件通过）。

## 4. 未达标时怎么办

| 情况 | 处理 |
| --- | --- |
| 红线不达标 | POC 判负，回到设计而非调参；尤其「源端新增 ≠ 0」意味着方案违反了设计红线 |
| fixture 出现失配 | 直接触发 02 文档的 A/B 路径重新评估，可能需要换路径 |
| 规模未达实测反推的目标 | 先查队列隔离与配额配置（06 文档）与数据通路带宽，再考虑扩容 |
| 效率目标未达 | 优先检查网络拓扑（20M/s 的跨机房传输是最常见的原因） |
