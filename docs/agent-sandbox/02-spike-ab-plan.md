# 02 · A/B 路径对照 Spike 实验方案

> 对应计划「阶段 0 · 技术预研」与「可立即产出 · 第 2 项」，攻关「难点 1」。
> 目的：用可复现的证据把 E2（ChangeSet 差异引擎）的估算依据等级从 **L3（路线未定）** 降到 **L2（路线明确）**。
> **第二轮复核修订**：① 比对口径改为净状态差（第一轮的 STEP 5 判据不可能通过）；
> ② 新增第 7 节「数据通路实测」，作为阶段 0 的**第三个出口判据**。

## 1. 时间盒与出口判据

| 项 | 约定 |
| --- | --- |

| **出口判据 4（第二轮新增）** | **沙盒数据通路的有效带宽与并发衰减曲线已实测**，见第 7 节。测不出目标量级 → 先下调对外指标，再谈开发 |
| 失败处理 | 任一出口判据不达标 → 项目维持预研状态，不进入阶段 1 |

## 2. 两条路径的定义

| 路径 | 实现 | 需要预先确认 |
| --- | --- | --- |
| **A · 块级差异翻译** | 读取 COW 快照的块级变化，反查数据文件结构还原到表/行 | 是否已有 InnoDB / Oracle 数据块解析代码可复用（开放问题 #6） |
| **B · 逻辑日志解析** | 在**沙盒库**上开启 binlog(ROW, full image)/LogMiner，解析为行级变更 | 沙盒模板是否允许默认开启日志；额外空间与 TPS 开销 |

> 红线复核：路径 B 的日志只在沙盒库开启，**源端零改动**。任何需要在源端开日志的方案直接出局。

## 3. 标准操作序列（fixture）

固定脚本见 [`spike/fixtures/workload.mysql.sql`](spike/fixtures/workload.mysql.sql)，
覆盖以下必须被正确还原的语义：

| # | 操作 | 考察点 |
| --- | --- | --- |
| 1 | 单行 INSERT | 基础 insert，after 镜像完整性 |
| 2 | 单行 UPDATE（改 2 列） | before/after 双镜像与 `changed_columns` 精确性 |
| 3 | 单行 DELETE | before 镜像是否保留（块级路径的典型弱项） |
| 4 | 批量 UPDATE（影响 500 行） | 行数规模下的完整性与性能 |
| 5 | 同一行被连续修改 3 次 | **两条路径都必须折叠为 1 条 update**（before=最初值，after=最终值）。见下方说明 |
| 6 | 插入后在同一事务内删除 | 净效果为零的变更是否被误报 |
| 7 | 回滚的事务 | **必须不出现在 ChangeSet 里**（块级路径的高风险点） |
| 8 | `ALTER TABLE ADD COLUMN` | DDL 识别与风险定级 |
| 9 | 无主键表的 UPDATE | 是否正确降级为 `completeness=unknown` 而不是静默漏报 |
| 11 | 先 DELETE 后以同主键 INSERT | 折叠为单条 update（01 文档折叠规则）|
| 10 | 大字段（TEXT/BLOB）更新 | 边界 5.4 行为是否一致 |

每条操作都在 fixture 中标注了**期望的 ChangeSet 语义**，便于人工核对。

### 3.1 STEP 5 判据的修订（第一轮的设计错误）

第一轮写的是「是否正确折叠为净变更 **or** 保留操作序列」，并要求两条路径给出**相同表示**。
这是一个**永远无法通过的判据**：逻辑日志天然是操作序列（3 条），块级差异天然是净状态差（1 条），
二者对同一组操作在定义上就不可能相同。等于把实验设计成了必然失败。

修订后：[01 文档](01-changeset-model.md)已把 ChangeSet 的规范形式**唯一确定为净状态差**，
逻辑日志路径必须在输出前完成折叠。于是 STEP 5 的期望结果是唯一的：
**1 条 update，`before` 为第一次修改前的值，`after` 为第三次修改后的值。**
这样判据才既明确又可能通过。

## 4. 比对方法

比对脚本：[`spike/compare_changesets.py`](spike/compare_changesets.py)

**比对的对象是净状态差**，不是操作历史。规范化掉两条路径天然不同、且不影响语义的字段：

- 行顺序（净差无序，按 `表 + 主键` 排序后比对）；
- `txn_id` / `position` / `occurred_at`（**溯源信息，不参与比对**；块级路径下恒为 null，这是正常的）；
- `changed_columns` 的顺序；
- `checksum` / `bytes_scanned` / `captured_at` / `changeset_id`。

**不允许**存在差异的部分（任何差异都判定实验失败）：

- 表集合、每表的 insert/update/delete 计数；
- 每一行的 `op`、`pk`、`before`、`after`、`changed_columns` 集合；
- `ddl_changes` 的 `ddl_type` / `object` / `risk`；
- `integrity.completeness`。

脚本输出四类结论：

| 结论 | 含义 | 处理 |
| --- | --- | --- |
| `EQUIVALENT` | 两条路径的净差一致 | 通过 |
| `ONLY_IN_A` / `ONLY_IN_B` | 某一侧缺少该行的净变更 | **最严重**，该路径直接判负 |
| `MISMATCH` | 同一行的 op / before / after / changed_columns 不一致 | 判负 |
| `TRACE_ONLY_DIFF` | 仅溯源字段不同 | **忽略**，不算差异 |

第一轮把「某一侧没有」一律叫 `MISSING`（漏报），措辞是错的：当两条路径语义类型不同时，
那不是漏报，是语义类型不匹配。修订后规范形式已统一为净差，`ONLY_IN_*` 才真正等同于漏报。

对应的 POC 指标口径也已修订（见 [08 文档](08-poc-acceptance.md)）：
「一致率 = 100%」这种抽样不可证明的表述，改为
**「fixture 全集上零失配」（全量可判定）+「生产负载下的失配率上界（带置信区间）」**。

## 7. 数据通路实测（第二轮新增，阶段 0 第三出口判据）

### 7.1 为什么必须前置

白皮书实测：DCM ↔ 挂载端约 **20 MB/s**，而挂载端就是沙盒的数据通路。算一笔账：

| 项 | 数值 |
| --- | --- |
| 5 分钟内该链路总吞吐上限 | ≈ **6 GB** |
| 100 并发沙盒 × 每个 10 MB/s 轻量读写 | 需 **1000 MB/s** |
| 差距 | **约 50 倍** |

同时，白皮书唯一的挂载实测是「备份副本挂载 **6 分钟**」，且很可能是命中快照的**最优单例**（假设 A3），
而第一轮却把 P95 目标定成了 **< 5 分钟**——比唯一的最优实测值还激进。这是典型的目标值拍脑袋。

第一轮只在 [06 文档](06-orchestration.md)写了一句「建议同机房部署」，
把一个**量级级别的架构约束**降格成了部署建议。

### 7.2 实测内容（1-2 人天）

| 测项 | 方法 | 输出 |
| --- | --- | --- |
| 单沙盒创建端到端耗时 | 命中快照 / 需回放日志两种 timing_mode 各 10 次 | 中位数与 P95 |
| 挂载链路有效带宽 | 顺序读、随机读、混合读写各测 | MB/s |
| **克隆是否为零拷贝** | 创建沙盒时观测网络实际传输字节数 vs 库体量 | 验证/否定假设 A1 |
| 并发衰减曲线 | 并发 1 / 5 / 10 / 20 / 50 沙盒 | 单沙盒耗时随并发的变化曲线 |
| 拓扑影响 | 同机房 vs 跨机房各测一次 | 差异倍数 |

### 7.3 SLA 必须由实测反推

纪律：**先测单沙盒在真实链路上的耗时，再乘以并发衰减系数得出承诺值**，
而不是先写一个漂亮数字再想办法达成。若实测无法支撑 100 并发，
就在 [08 文档](08-poc-acceptance.md)下调该指标，而不是等 POC 阶段才发现所有性能承诺都不成立。
