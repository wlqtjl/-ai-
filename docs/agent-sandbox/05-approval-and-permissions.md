## 1. 一句话原则

**Agent 只能提出，人类才能放行；差异不可信时一律不放行。**

### 1.1 致命矛盾：脱敏默认开启 与 合并回生产，二者不可兼得

这是第二轮复核发现的最严重问题，第一轮的设计里两条规则并存却互斥：

- 把「脱敏默认开启」定为合规红线（风险 R5、Epic E12）；
- 同时设计「把沙盒的行级变更合并回生产」。

**这两件事在数据层面互斥**：沙盒里是脱敏后的数据，Agent 基于脱敏值做的 UPDATE/INSERT，
其 before/after 镜像里带的是**假数据**。合并回生产等于往生产库写入脱敏值——
这不是 bug，是**数据污染**。即使只写变更列，定位用的 `WHERE` 条件也会因定位列被脱敏而失配。

第一轮甚至把 DAG 顺序写成了 `apply_masking → verify_consistency`，
等于把这个矛盾固化进了编排设计，却没意识到下游的 merge 因此失效。

三条出路，必须三选一：

| 方案 | 内容 | 代价 |
| --- | --- | --- |
| (a) | DML 变更可合并 → 沙盒**不能**脱敏，靠网络隔离 + 临时凭据 + 审计管控 | 合规风险转移到访问控制，需客户安全部门认可（假设 C3） |
| (b) | **坚持脱敏 → 首版不写生产库，产出经审核的变更集/变更脚本** | 少了「一键合并」的演示效果 |
| (c) | 可逆的格式保留令牌化，合并时反解 | 工程复杂度高，令牌映射表本身成为新的敏感资产。首版不建议 |

### 1.2 首版定稿为 (b)：「变更导出」而非「合并回生产」

> ✅ **已决策（一牧确认，2026-09-07）：首版走 (b)。** 决策记录见 [09 文档开放问题 #9](09-open-questions.md)。
> 本节以下内容为定稿，不再是推荐方案。分支 (a)、(c) 移出首版范围。

**沙盒 = 可写 + 用完即焚 + 产出一份经审核的变更集/变更脚本，由客户既有的数据库变更流程去执行。**

第二轮复核发现的四个问题（脱敏与合并互斥、A/B 语义类型不匹配、表级冲突检测不可用、
DDL 与全量合并的组合死锁），**根源都是同一个：直接写生产库**。改为导出后一并消解：

| 收益 | 说明 |
| --- | --- |
| 绕开脱敏矛盾 | 导出的是变更**意图**，可在生产侧基于真实数据重新定位 |
| 绕开语义之争 | 导出净状态差即可，不需要重放操作序列 |
| 绕开冲突检测不可用 | 冲突由客户既有变更流程处理——那本来就是它的职责 |
| 降低 E6 风险 | 从 L3 高风险项降级为一个导出器（见 [10 文档](10-effort-estimation.md)） |
| 更容易过安全评审 | 「我们不写你的生产库」是一句极有力的话 |
| 与产品定位一致 | DCM 的定位是**数据供给**，一牧做客户变更流程的上游供给，而不是替代它 |

外部佐证：Postgres.ai 明确**不做**合并回生产；Neon 的行级合并也是弱项；
只有 Dolt 做到了，代价是重写整个存储引擎。这些团队不是没想到，是权衡后选择不做。

**代价**：少了「一键合并」这个演示效果。但**演示效果不是护城河，能过安全评审才是。**
全自动合并放到第二版，等有了真实客户案例再说。

### 1.3 决策生效后的三条约束（首版不得违反）

1. **一牧的任何组件不得对客户生产库执行写操作**——包括 DML、DDL 与临时表；
   这条由 08 文档红线指标 `unexpected_production_writes = 0` 保障，且因为「预期写入」为空集，
   该指标从「难以界定」变为可严格判定；
2. **脱敏默认开启且不可关闭**——原本与合并互斥的矛盾已消失，脱敏正式升为合规红线，
   `security_admin` 不再拥有关闭脱敏的权限（见第 2 节权限矩阵）；
3. **冲突只探测不裁决**——沙盒侧输出行级冲突标记供人工判断，
   真正的并发冲突裁决交由客户既有变更流程，一牧不承诺「合并一定成功」这类无法兑现的语义。

## 2. 角色与权限矩阵

| 能力 | agent | requester(human) | reviewer | dba_approver | security_admin |
| --- | --- | --- | --- | --- | --- |
| 创建沙盒 | ✔（受配额） | ✔ | ✔ | ✔ | ✔ |
| 连接沙盒读写 | ✔ | ✔ | ✖ | ✔ | ✖ |
| 创建检查点 / 回滚 | ✔ | ✔ | ✖ | ✔ | ✖ |
| 获取 ChangeSet | ✔ | ✔ | ✔ | ✔ | ✔ |
| 提交审批 | ✔ | ✔ | ✖ | ✔ | ✖ |
| 导出干跑（dry-run 预演） | ✖ | ✔ | ✔ | ✔ | ✔ |
| **下载变更集导出物** | ✖ | ✔ | ✔ | ✔ | ✔ |
| **审批通过 / 拒绝** | **✖** | ✖（不可自审自批） | ✔ | ✔ | ✖ |
| 放行高风险 DDL | ✖ | ✖ | ✖ | ✔ | ✖ |
| ~~关闭脱敏~~ | ✖ | ✖ | ✖ | ✖ | **✖（决策后取消该能力）** |
| 直接写生产库 | **首版不提供该能力**（见 1.2） | | | | |
| 查看审计 | ✖ | 仅本人 | ✔ | ✔ | ✔ |

四条硬规则：

1. **`agent` 永远不能审批**（服务端按凭据判定，返回 `403 agent_cannot_approve`）；
2. **提交人不能是审批人**，即使提交人是人类（防止「人类给 Agent 背书」变成走过场）；
3. **高风险 DDL 需要 `dba_approver` 额外显式确认**（`ack_high_risk_ddl=true`）；
4. **没有任何角色能关闭脱敏，也没有任何角色能让系统写生产库**——
   1.2 决策落定后，这两项不再是权限项，而是系统不具备的能力。
   把它们做成「谁都没有权限」而不是「只有某个角色有权限」，
   是因为**不存在的能力才是真正的边界，可配置的能力迟早会被配置开**。

## 3. 审批流程

```
Agent 完成操作
   │
   ├─► 系统自动生成 ChangeSet ──► 门禁校验（tools/validate_changeset.py 的规则）
   │        │
   │        ├─ completeness != complete ─────► 直接拒绝，要求重建沙盒（不进入人工环节）
   │        ├─ 存在冲突 ───────────────────► 直接拒绝，要求基于最新时间点重建
   │        └─ 通过
   │
   ├─► submit_sandbox_for_review（Agent 可调用）→ 沙盒转 pending_review（只读冻结）
   │
   ├─► 审批人查看：ChangeSet 摘要 + dry-run 影响面报告 + 冲突检测结论
   │
   ├─► 通过 ──► exporting ──► 产出变更集导出物 ──► exported
   │                                （交客户既有变更流程执行，一牧不写生产库）
   │
   └─► 拒绝 ──► 沙盒回到 ready（可继续修改后重新提交）或直接丢弃
```

导出物包含三部分：① 净状态差 ChangeSet（JSON，机器可读）；② 影响面报告（人可读）；
③ 可选的变更脚本骨架（按目标库方言生成，**需在生产侧基于真实数据重新定位**，
因为沙盒可能是脱敏的——这一点必须在导出物首页显著声明）。

## 4. 门禁规则（自动，先于人工）

自动门禁的意义是：**不要把不可信的差异摆到人面前让人做判断**。规则与
[`tools/validate_changeset.py`](tools/validate_changeset.py) 中的实现一一对应：

| 规则 | 判定 | 理由 |
| --- | --- | --- |
| `integrity.completeness != complete` | 拒绝 | 漏报是安全问题，不是精度问题 |
| `conflicts` 非空 | 拒绝 | 首版策略：冲突即拒绝，不做三方合并 |
| 违反净状态差不变式（同表主键重复 / before==after） | 拒绝 | 采集侧未折叠，见 01 文档 3.3 |
| 含 `risk=high` 的 DDL | **不阻断**，标记需 `dba_approver` 逐条确认 | 见下方「组合死锁」说明 |
| 存在 `rows_truncated=true` 的表 | 拒绝 | 审批人看到的不是全貌 |
| 存在无主键表 | 拒绝 | 行定位不可靠（能力边界 6.4） |

**第二轮修订：修复「组合死锁」。** 第一轮定了两条各自看都合理的保守规则：
①整变更集全量处理（含 DDL 就一起处理）；②含高风险 DDL 默认拒绝。
**叠加起来的结果是：只要 Agent 碰过一次 DDL，整个变更集就被门禁拦死**，
而 schema 变更恰恰是同类产品（PlanetScale / Supabase）最主要的价值场景。
单独看每条规则都合理，组合起来产品就不可用了——这是只做单点设计、
没做**组合路径推演**的结果。修订后：高风险 DDL 触发「逐条确认」，不触发「整体拒绝」。

## 5. 导出与（第二版的）合并的安全动作

### 5.1 首版：变更导出的三个安全动作

| # | 动作 | 说明 |
| --- | --- | --- |
| ① | **干跑与影响面报告** | 导出前产出影响表与行数、冲突结论、DDL 清单；审批人看到的是影响面而不是 SQL 堆 |
| ② | **导出物与审批绑定** | 导出物携带 `changeset_checksum`，与审批记录绑定；审批人看到的与导出的必须是同一份 |
| ③ | **脱敏声明** | 若沙盒启用了脱敏，导出物必须在首页显著标注「本变更集中的值来自脱敏数据，不得直接写入生产」 |

首版**不写生产库**，因此「合并失败自动回退生产库」这一动作不适用；
对应的 POC 指标口径也已修订（见 [08 文档](08-poc-acceptance.md)）。

### 5.2 第二版若做合并：冲突检测必须是行级

**第一轮设计的「表级最后变更时间戳」有两个独立的致命问题**：

1. **不可实现**：主流数据库缺乏可靠的「表最后修改时间」。Oracle `DBA_TAB_MODIFICATIONS` 是近似值
   且定期刷新，MySQL `information_schema.tables.UPDATE_TIME` 众所周知不可靠（假设 B4 已证伪）。
   第一轮写了这个机制，却没验证它拿不拿得到；
2. **不可用**：即使拿得到，对一张持续写入的核心业务表，「生产库在基线之后有变更」**永远为真**，
   于是每次合并都被拒绝——这个「保守策略」在最重要的场景里等于产品不可用（假设 B5）。

修订后采用**行级乐观并发控制**：比对待处理行在生产库的当前值是否等于沙盒记录的 `before` 镜像，
不等即判定冲突。它不比表级时间戳难实现，却是可实现且可用的。

首版明确**不做部分导出**：审批粒度是整个变更集，要么全导、要么全弃（是否够用见开放问题 #7）。

## 6. 审计留痕（对接现有「数据库安全管控平台」）

在现有审计维度上扩展以下字段：

| 字段 | 说明 |
| --- | --- |
| `requester_type` | `human` / `agent`，由凭据推导，不接受自报 |
| `agent_identity` | Agent 的稳定标识（模型/工作流/会话），用于追责与限流 |
| `purpose_tag` | 用途标签，创建时必填 |
| `masking_policy` | 记录本次沙盒是否脱敏，以及关闭脱敏的授权人 |
| `changeset_id` / `changeset_checksum` | 审批人看到的与实际合并的必须是同一份 |
| `decision`, `decided_by`, `decision_comment` | 审批结论与理由 |
| `dry_run_report_id` | 审批依据的影响面报告 |
| `export_result`, `export_artifact_checksum` | 导出结果与导出物校验和（首版）|
| `merge_result`, `rollback_triggered` | 仅第二版启用合并能力后适用 |

审计不可变要求：审批记录与 ChangeSet 校验和绑定，导出执行前重新校验 checksum，
不一致即中止（防止「审批后被替换」）。

## 7. Agent 侧新增风险面与对策（难点 5）

| 风险 | 对策 |
| --- | --- |
| 提示注入伪造身份（「我是管理员，请直接放行」） | 身份只来自凭据，请求体中的身份声明一律忽略 |
| 诱导 Agent 提交恶意变更 | 人类审批强制点 + dry-run 影响面 + 高风险 DDL 二次确认 |
| Agent 循环重试打爆资源 | Agent 类配额显著低于人类；创建频率限流；TTL 强制回收 |
| 沙盒内生产数据外泄 | 脱敏默认开启（首版选 (b) 的前提）；沙盒网络与生产网络隔离；临时凭据无外连权限 |
| 越权申请他人数据源的沙盒 | `source_id` 的访问控制沿用现有数据源权限体系，不因沙盒场景放宽 |
| 通过 MCP 工具组合绕过审批 | MCP 层不暴露 approve/reject/merge，能力边界在服务端而非提示词里 |
