## 一句话说明（大白话）

**这份文档在算「大概要投多少人力」，并且诚实标注每个数字有多可信。**

每项工作都标了可信度：

- **L1** = 有现成的东西可以参考，比较准；
- **L2** = 路线清楚但没做过，有偏差；
- **L3** = 连怎么做都还没定，**这种不许进排期**，只能先做预研。

**这里也犯过一个错**：我把每项的乐观值加起来当成「最好情况」，悲观值加起来当成「最坏情况」。
这在统计上是错的——它等于假设「所有事同时最顺」或者「所有事同时最糟」，
而现实中这两种极端几乎不可能发生。所以那个区间是**假宽**的。

现在改用模拟计算（跑一万次随机组合），给出一个更接近现实的区间。

还有一条：那个「自己解析数据库文件格式」的方案，我原来给了个「看起来保守」的数字。
其实它相当于自研半个数据库引擎，**给数字本身就是错的**——给了数字，就等于承认它可以被排期。
现在直接标「首版不做」。

给谁看：管理层、排期负责人。

## 1. 规则

| 依据等级 | 含义 | 是否可进排期承诺 |
| --- | --- | --- |
| **L1** | 有可直接参照的既有代码 | 可 |
| **L2** | 技术路线明确，但需新写 | 可（带三点估计） |
| **L3** | 技术路线未定 | **不可**，只能进预研，先做 spike 收敛 |

三点估计记为「乐观 / 最可能 / 悲观」，期望值按 PERT：`(O + 4M + P) / 6`。

## 3. 合计（不含 E10）

数字由 `python3 tools/estimate_montecarlo.py` 产出（10 万次抽样，PERT-Beta，seed 固定可复现）：

| 口径 | 人天 |
| --- | --- |
| **P10** | **123** |
| **P50** | **133** |
| **P90** | **144** |
| 均值（≈ PERT 期望之和 134） | 133 |

按 3-4 人研发小队全职投入，P50 对应约 **2.5-3.5 个月**。

### 3.1 为什么删掉了第一轮的「76 - 265」

第一轮把各 Epic 的乐观值直接相加得 76、悲观值相加得 265。**这在统计上是错的**：
它隐含「所有 Epic 同时命中最好 / 最坏情况」，而这些事件近似独立，同时全中的概率接近于零。
结果是一个既没意义、又会被人当成承诺边界来用的区间。

作为对照，本表当前口径下简单相加会得到 **73 - 216**，而蒙特卡洛给出的 P10-P90 是 **123 - 144**——
真实区间窄得多。**期望值可以相加**（PERT 期望具有线性性质，134 这个数成立），**区间不可以**。

**重要限定**：模拟假设各 Epic 相互独立。若存在共同失败因子
（例如假设 A2「带宽不足」会同时拖慢 E1/E9/E13），真实区间比上表更宽。
引用这组数字时必须一并说明这个前提。

## 4. 必须显式声明的四件事

1. **E2 仍需 spike 先行**。虽然路径收窄后依据等级降到 L2，但假设 B2
   （逻辑日志可无损折叠为净差）尚未验证，spike 未通过前不得进排期承诺。
2. **块级差异路径不给估算，直接标「首版范围外」**（第二轮修订）。
   第一轮给了它「悲观 60 人天」，看起来保守，实际上反而掩盖了真实风险：
   它的实质是**自研 InnoDB / Oracle 数据块解析器并保证无损**，
   是同类公司多年积累的核心资产，不是 60 人天能做完、并敢用于产出变更集的东西。
   **给一个数字，就等于承认它可以被排期。** 正确的表述是：
   「正确性无法在可接受成本内证明，而漏报是安全问题，故首版不做。」
3. **本表新增 E12（脱敏默认开启）**。原报告把脱敏列为风险项但未计入工作量；
   既然把它定为「默认选项而非可选项」，就必须有对应的工作量。
4. **E6 大幅降险**（第二轮修订）：首版改为变更集导出后，
   它从「写生产库的高风险 L3 项」变成「一个导出器 + 只读冲突探测」，
   期望值由 17.2 降到 10.7，且不再依赖开放问题 #1 的答案。
