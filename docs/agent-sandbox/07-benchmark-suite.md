## 一句话说明（大白话）

**这份文档在设计「怎么测性能，才能让不同时间测出来的数字可以互相比较」。**

常见的毛病是：这次测用 10 GB 数据，下次测用 100 GB，然后说「性能提升了」——这种对比没有意义。

所以要**固定**三样东西：用多大的数据、开多少个沙箱、跑哪些操作。固定之后，
不同版本、不同环境测出来的数字才能画在同一张曲线上。

**最重要的一条纪律**：先测**单个**沙箱要多久，再往上推并发能到多少，
**不许反过来先定一个好听的目标再去凑**。上一轮就犯了这个错：
唯一一个实测值是「挂载 6 分钟」，我却把目标写成了「95% 的情况 5 分钟内完成」——比实测的最好成绩还激进。

给谁看：研发、测试。

## 1. 为什么需要它

第十二部分的性能基线来自白皮书的零散实测，场景（少量大副本）与 Agent 沙盒（大量小沙盒）差异巨大，
直接引用会导致对外承诺失真。基准测试套件的目标是产出**可纵向对比、可横向对比**的数字：

- **纵向**：每次版本迭代跑同一套负载，形成趋势曲线，能发现性能回退；
- **横向**：用同一套负载在 Neon / Postgres.ai 上跑一遍，得到可比数字——
  这比任何竞品分析文字都更有说服力（也更能回答开放问题 #8）。

## 2. 固定要素（一旦确定不得随意更改）

### 2.1 数据集

| 规格 | 表数 | 总行数 | 数据体量 | 用途 |
| --- | --- | --- | --- | --- |
| `tiny` | 10 | 100 万 | ~1 GB | 冒烟与 CI |
| `small` | 50 | 5000 万 | ~50 GB | 常规回归 |
| `medium` | 200 | 5 亿 | ~500 GB | 接近真实客户业务库 |
| `large` | 500 | 30 亿 | ~3 TB | 极限与容量规划 |

数据生成必须**确定性**（固定随机种子），保证任何人任何时间生成的数据集完全一致。

### 2.2 并发模型

| 模型 | 描述 | 对应真实场景 |
| --- | --- | --- |
| `M0 单例基线`（**第二轮新增，必须先跑**） | 单沙盒，无并发 | 一切并发目标的推导起点；不测它就没有反推 SLA 的依据 |
| `M1 突发` | 60 秒内创建 **N** 个沙盒 | CI 流水线批量触发的 Agent 任务 |
| `M2 稳态` | 维持 **N** 个存活沙盒，平均生命周期 30 分钟，泊松到达 | 日常 Agent 工作负载 |
| `M3 长尾` | 90% 短沙盒（<10 分钟）+ 10% 长沙盒（>4 小时） | 真实混合负载 |
| `M4 竞争` | 沙盒负载与备份/容灾任务同时运行 | 验证队列隔离是否有效（06 文档第 2 节） |

**N 的取值不得预设。** 第一轮直接写 100，而白皮书实测的数据通路只有约 20 MB/s，
与 100 并发的需求差约 50 倍。正确做法是：先跑 `M0` 得到单沙盒真实耗时与带宽占用，
再按并发衰减曲线反推 N，然后才写进对外指标。

### 2.3 操作序列

复用 spike 的 fixture（[`spike/fixtures/workload.mysql.sql`](spike/fixtures/workload.mysql.sql)），
保证「性能测试」和「正确性测试」跑的是同一组语义，不会出现「快但错」的结论。

## 3. 必测指标

| 类别 | 指标 | 采集点 |
| --- | --- | --- |
| 创建 | `near_current` 创建耗时 P50/P95/P99 | API 受理 → state=ready |
| 创建 | `point_in_time` 创建耗时（按回放跨度分桶：1h/6h/24h/72h） | 同上 |
| 创建 | 预估准确度：`|estimated_ready_at - 实际就绪| / 实际耗时` | 直接检验 SLA 承诺是否可信 |
| **通路** | **有效带宽、克隆是否零拷贝、跨机房 vs 同机房差异**（第二轮新增） | 一切性能结论的前提，见 02 文档第 7 节 |
| 规模 | 单集群并发存活沙盒上限（拐点法：耗时 P95 超阈值时的并发数） | 压测 |
| 差异 | ChangeSet 生成耗时 vs 变更行数（1k / 10k / 100k / 1M） | E2 性能可行性 |
| 差异 | ChangeSet 正确性：**fixture 全集零失配**（compare_changesets.py） | 全量可判定，非抽样；口径见 08 文档 2.1 |
| 导出 | 变更集导出耗时、成功率 | 首版不写生产库，故无「回退触发次数」 |
| 资源 | **每 GB 写入的存储放大倍数**、CPU、内存 | 成本模型；第一轮用「占全量克隆比例」，分母选得不对 |
| 资源 | 回收耗时与孤儿资源数量 | 泄漏检测 |
| 隔离 | M4 模型下备份任务的耗时劣化幅度 | 队列隔离是否有效 |

## 4. 横向对比设计

对可公开获取的产品（Neon、Postgres.ai/DLE、Supabase）跑**同一套**负载，只对比可比部分：

| 可比 | 不可比（须在报告中说明） |
| --- | --- |
| 分支/沙盒创建耗时 | 数据库引擎不同（一牧面向 Oracle/DB2 等存量库） |
| 并发分支数上限 | 部署形态不同（SaaS vs 私有化） |
| 差异摘要的颗粒度（schema/表/行） | 数据体量与硬件规格 |
| 是否支持合并回主干及其颗粒度 | 是否需要改造源端（**这是一牧的关键差异项，必须单独列出**） |

诚实原则：横向对比若在某项落后（大概率在「创建耗时」上落后于云原生产品），
应如实呈现并说明取舍——一牧的价值主张不是更快，而是**能作用于存量异构生产库且不改造源端**。

每次运行产出一份 JSON 结果文件，字段固定，便于自动生成趋势曲线：

```json
  "git_ref": "...",
  "dataset": "small",

```

## 6. 运行纪律

- 每个 milestone 至少跑一次 `small` + M2；发版前跑 `medium` + M1/M3/M4；
- 结果入库并画趋势图，**不允许**只在评审会上口头引用单次实测值；
- 硬件、网络拓扑、数据库版本随结果一并记录，否则数字不可比。
