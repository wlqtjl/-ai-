## 一句话说明（大白话）

**这份文档在教「怎么问客户，才能问出真话」。**

问客户「你以后会不会用 AI 干这个」，是出了名的不可靠——**大家都会说会**，
因为说「会」不用付任何代价。

所以判断标准不看嘴上怎么说，**看有没有实际投入**：有没有立项？有没有预算？
有没有相关工单？有没有已经在试的？说得头头是道但一分钱没花的，不算数。

还有两条：

1. **必须找几家不是现有客户的来问**。只问现有客户，人家碍于关系会捡好听的说，问不出真话；
2. **「愿意花多少钱」只问管钱的人**。不管钱的人说「愿意买」，这话不作数。

给谁看：产品、商务。**这是开工前必须先做完的三件事之一。**

---

> 对应计划「可协助做判断 · 第 13 项」，落实报告 18.4「先证明客户会买，再证明技术能做」。
> **这是阶段 0 的三个出口判据之一**（另两个是 A/B spike 与数据通路实测），
> 与技术工作并行进行，不是可选项。
> **第二轮复核修订**：样本设计存在系统性偏差，判据由「能说出场景」升级为**行为证据**。

## 1. 样本与验收判据

| 项 | 要求 |
| --- | --- |
| 样本量 | 5-8 家，其中**必须包含 1-2 家非现有客户**作为对照 |
| 行业覆盖 | 金融、运营商、政企各至少 1 家 |
| 角色覆盖 | 每家至少访谈 2 个角色（测试负责人 / DBA / 安全负责人） |
| **验收判据** | **至少 3 家能拿出「行为证据」**（定义见 1.2），仅「能说出场景」不算达标 |
| 付费意愿 | **只问有预算权的人**，其他角色的付费回答不计入结论 |
| 未达标处理 | 项目降级为技术预研，不进入产品立项（对应风险 R1） |

### 1.1 为什么必须含非现有客户（第二轮修订）

第一轮写的是「5-8 家**现有 DCM 客户**」，这有两重系统性偏差：

1. 现有客户天然友好、倾向给正面反馈；
2. 他们已经买了 DCM，回答「愿不愿意用」时存在**承诺一致性偏差**
   （为已做的购买决策辩护）。

没有对照组，就无法把「真实需求」与「样本偏差」区分开。

### 1.2 判据升级：从「说得出场景」到「行为证据」

**问客户「未来会不会用 AI Agent」是出了名的不可靠。** 因此判据改为可核查的行为证据，
以下任一即可计入达标：

| 行为证据 | 核查方式 |
| --- | --- |
| 已有 Agent 相关的**预算或立项** | 请对方说出立项名称与预算区间 |
| 已有相关的**工单或需求单** | 请对方描述单号与处理结果 |
| 已做过 **PoC / 试点**（哪怕失败了） | 请对方说出时间、参与人、结论 |
| 已有人**自建土办法**在跑 | 请对方描述脚本/工具与维护成本 |

**说得出场景但没有任何投入的，不计入达标。** 这一条是硬的：
「我们也想做，等有成熟方案就上」是最常见的假信号。

判据中「具体」的含义不变：「我们也在关注 AI」不算，
「我们的自动化回归测试需要每天造 200 条订单测试数据，现在是 DBA 手工跑脚本」才算——
但这仍只是**必要条件**，还需配上上表的行为证据。

## 2. 访谈纪律

1. **不做产品演示、不描述方案**——先问现状，再问需求；演示会污染答案；
2. **问事实，不问意愿**：「你上次这么做是什么时候」优于「你会不会用」；
3. **每个「愿意」都要追问代价**：愿意付费多少？愿意为它改流程吗？谁签字？
   **且只有对方确实有预算权时，付费回答才计入结论**；否则只作为背景信息记录；
4. **优先索取行为证据**：每当对方表达需求，追问「这件事你们已经投入了什么？」——
   预算、工单、试点、自建脚本，任何一项都比一句「有需求」更有信息量；
5. 全程记录原话，不做归纳式转述（对应 18.2「区分事实、推断与假设」）。

## 3. 角色 A · 测试负责人 / 研发经理

**目标：验证需求真实存在，并量化当前痛点。**

1. 你们团队现在有没有在用 AI Agent 做和数据库相关的事？具体是哪些任务？（若无 → 跳到 Q4）
2. 这些 Agent 现在怎么拿到数据？谁给的权限？是只读还是可写？
3. 上一次 Agent 因为「不能写数据库」而做不下去的具体任务是什么？最后怎么解决的？
4. 现在测试团队申请一份新鲜测试数据，从提出到拿到手要多久？中间经过几个人？
5. 这份数据用完之后怎么处理？会不会长期占着？
6. 如果 Agent 在测试库里写坏了数据，现在的恢复流程是什么？花多久？
7. 你们有没有自己搭过类似「快照 + 快速恢复」的土办法（ZFS/LVM/脚本）？维护成本如何？
   （**对应竞品台账 C14，这是最重要的一题**）

---

## 4. 角色 B · DBA / 数据库运维负责人

**目标：验证技术方案的接受度，以及「变更导出 vs 直接合并」的真实诉求（开放问题 #9）。**

1. 你们现在允许非生产环境用生产数据吗？必须脱敏吗？谁批？
2. 一个数据变更从测试环境合并到生产，现在的流程是什么？谁审？平均多久？
   （**Q-B2：直接验证假设 C2。若客户没有成熟的变更执行流程，「变更导出」这条首版路线就失去落点**）
2b. 如果我们**不写你的生产库**，只给你一份经审核的变更集，由你们现有流程去执行——
   这对你来说是减分项还是加分项？（**验证开放问题 #9 的推荐分支 B**）
3. 审批时你实际看的是什么？SQL 脚本、变更单，还是影响行数？
   （**决定 ChangeSet 摘要该长什么样**）
4. 如果给你一份「这次变更影响 3 张表、120 行」的结构化摘要，够你做判断吗？还缺什么？
5. 你能接受「要么全合并、要么全丢弃」吗？还是必须能挑着合？
   （**对应开放问题 #7，直接决定 E6 范围**）
6. 如果合并到生产失败了，你希望系统怎么处理？自动回退你敢用吗？
7. 你最担心 Agent 操作数据库的哪一点？（记录原话）
8. 源端（生产库）如果需要装个 Agent 或开个挂载权限，你们能接受吗？
   （**验证设计红线的价值——预期答案是"绝对不行"**）

---

## 5. 角色 C · 安全 / 合规负责人

**目标：验证合规边界与审计诉求。**

1. AI Agent 访问生产数据，在你们的安全制度里现在归哪一类？有明确条款吗？
2. 沙盒里的数据必须脱敏吗？脱敏后还能满足测试需要吗？
   （**Q-C2：直接验证假设 C3。若必须脱敏，则 DML 变更永远不能直接写回生产——
   这是 05 文档 1.1 的致命矛盾，本题的答案决定首版走哪条分支**）
2b. 如果沙盒**不脱敏**，但做到网络隔离 + 临时凭据 + 全量审计，你们能接受吗？需要谁批？
3. 「Agent 提交、人工审批」这个模式，在你们的合规框架里能过吗？谁必须是审批人？
4. 你需要哪些审计字段才能事后追责？（记录清单，用于 05 文档第 6 节的字段扩展）
5. 如果 Agent 被诱导提交了恶意变更，你希望在哪一环被拦住？
6. 数据不出域、私有化部署，对你们是硬要求还是偏好？

---

## 6. 商业化问题（对所有角色）

1. 如果有这个能力，你期望它是 DCM 的内置功能，还是可以单独采购的模块？
2. 如果单独采购，按什么计价你觉得合理？（按沙盒数 / 按数据量 / 按订阅）
3. 你们采购这类能力的决策链是什么？谁是最终签字人？
4. **你们有没有考虑过用 Neon / Supabase / Postgres.ai 这类产品？为什么没用/用了？**
   （**对应开放问题 #8，是最能暴露真实竞争格局的一题**）

## 7. 记录模板

```
客户：            行业：            访谈日期：
受访者角色：      访谈人：

【现状事实】（原话记录，不归纳）

【已在跑的 Agent 场景】有 / 无：

【行为证据】（预算 / 立项 / 工单 / PoC / 自建脚本，逐项记录具体信息；无则明确写「无」）

【受访者是否有预算权】是 / 否　（否则本人的付费回答不计入结论）

【是否为现有 DCM 客户】是 / 否　（对照组样本必须标出）

【当前替代做法】

【最关心的风险】（原话）

【审批颗粒度诉求】全量合并可接受 / 必须可选择性合并 / 未明确

【付费意愿】

【判据达成】① 能说出具体 Agent 场景：是/否　② 能说出当前替代做法：是/否
```

## 8. 汇总与决策

访谈全部结束后产出一页纸结论，只回答三个问题：

1. 达成判据的客户有几家？（< 3 家 → 项目降级）
2. 审批颗粒度：多少家能接受「全量合并」？（决定 E6 范围）
3. 真实竞争对手是谁？（云原生产品 / 自建土办法 / 维持现状）——回填到 12 文档台账
