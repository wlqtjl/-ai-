# 13 · 客户访谈提纲与验收判据

> 对应计划「可协助做判断 · 第 13 项」，落实报告 18.4「先证明客户会买，再证明技术能做」。
> **这是阶段 0 的两个出口判据之一，与技术 spike 并行进行，不是可选项。**

## 1. 样本与验收判据

| 项 | 要求 |
| --- | --- |
| 样本量 | 5-8 家现有 DCM 客户 |
| 行业覆盖 | 金融、运营商、政企各至少 1 家 |
| 角色覆盖 | 每家至少访谈 2 个角色（测试负责人 / DBA / 安全负责人） |
| **验收判据** | **至少 3 家能明确说出：① 具体的 Agent 使用场景 ② 当前的替代做法** |
| 未达标处理 | 项目降级为技术预研，不进入产品立项（对应风险 R1） |

判据的关键是「具体」：「我们也在关注 AI」不算，「我们的自动化回归测试需要每天造 200 条订单测试数据，
现在是 DBA 手工跑脚本」才算。

## 2. 访谈纪律

1. **不做产品演示、不描述方案**——先问现状，再问需求；演示会污染答案；
2. **问事实，不问意愿**：「你上次这么做是什么时候」优于「你会不会用」；
3. **每个「愿意」都要追问代价**：愿意付费多少？愿意为它改流程吗？谁签字？
4. 全程记录原话，不做归纳式转述（对应 18.2「区分事实、推断与假设」）。

---

## 3. 角色 A · 测试负责人 / 研发经理

**目标：验证需求真实存在，并量化当前痛点。**

1. 你们团队现在有没有在用 AI Agent 做和数据库相关的事？具体是哪些任务？（若无 → 跳到 Q4）
2. 这些 Agent 现在怎么拿到数据？谁给的权限？是只读还是可写？
3. 上一次 Agent 因为「不能写数据库」而做不下去的具体任务是什么？最后怎么解决的？
4. 现在测试团队申请一份新鲜测试数据，从提出到拿到手要多久？中间经过几个人？
5. 这份数据用完之后怎么处理？会不会长期占着？
6. 如果 Agent 在测试库里写坏了数据，现在的恢复流程是什么？花多久？
7. 你们有没有自己搭过类似「快照 + 快速恢复」的土办法（ZFS/LVM/脚本）？维护成本如何？
   （**对应竞品台账 C14，这是最重要的一题**）

---

## 4. 角色 B · DBA / 数据库运维负责人

**目标：验证技术方案的接受度与合并回切的真实诉求。**

1. 你们现在允许非生产环境用生产数据吗？必须脱敏吗？谁批？
2. 一个数据变更从测试环境合并到生产，现在的流程是什么？谁审？平均多久？
3. 审批时你实际看的是什么？SQL 脚本、变更单，还是影响行数？
   （**决定 ChangeSet 摘要该长什么样**）
4. 如果给你一份「这次变更影响 3 张表、120 行」的结构化摘要，够你做判断吗？还缺什么？
5. 你能接受「要么全合并、要么全丢弃」吗？还是必须能挑着合？
   （**对应开放问题 #7，直接决定 E6 范围**）
6. 如果合并到生产失败了，你希望系统怎么处理？自动回退你敢用吗？
7. 你最担心 Agent 操作数据库的哪一点？（记录原话）
8. 源端（生产库）如果需要装个 Agent 或开个挂载权限，你们能接受吗？
   （**验证设计红线的价值——预期答案是"绝对不行"**）

---

## 5. 角色 C · 安全 / 合规负责人

**目标：验证合规边界与审计诉求。**

1. AI Agent 访问生产数据，在你们的安全制度里现在归哪一类？有明确条款吗？
2. 沙盒里的数据必须脱敏吗？脱敏后还能满足测试需要吗？
3. 「Agent 提交、人工审批」这个模式，在你们的合规框架里能过吗？谁必须是审批人？
4. 你需要哪些审计字段才能事后追责？（记录清单，用于 05 文档第 6 节的字段扩展）
5. 如果 Agent 被诱导提交了恶意变更，你希望在哪一环被拦住？
6. 数据不出域、私有化部署，对你们是硬要求还是偏好？

---

## 6. 商业化问题（对所有角色）

1. 如果有这个能力，你期望它是 DCM 的内置功能，还是可以单独采购的模块？
2. 如果单独采购，按什么计价你觉得合理？（按沙盒数 / 按数据量 / 按订阅）
3. 你们采购这类能力的决策链是什么？谁是最终签字人？
4. **你们有没有考虑过用 Neon / Supabase / Postgres.ai 这类产品？为什么没用/用了？**
   （**对应开放问题 #8，是最能暴露真实竞争格局的一题**）

---

## 7. 记录模板

```
客户：            行业：            访谈日期：
受访者角色：      访谈人：

【现状事实】（原话记录，不归纳）

【已在跑的 Agent 场景】有 / 无：

【当前替代做法】

【最关心的风险】（原话）

【审批颗粒度诉求】全量合并可接受 / 必须可选择性合并 / 未明确

【付费意愿】

【判据达成】① 能说出具体 Agent 场景：是/否　② 能说出当前替代做法：是/否
```

## 8. 汇总与决策

访谈全部结束后产出一页纸结论，只回答三个问题：

1. 达成判据的客户有几家？（< 3 家 → 项目降级）
2. 审批颗粒度：多少家能接受「全量合并」？（决定 E6 范围）
3. 真实竞争对手是谁？（云原生产品 / 自建土办法 / 维持现状）——回填到 12 文档台账
