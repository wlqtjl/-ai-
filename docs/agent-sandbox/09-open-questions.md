# 09 · 开放问题确认清单（评审会用）

> 对应计划「可协助做判断 · 第 9 项」，把报告第十五部分的 8 个开放问题变成**逐条可决策**的清单。
> 用法：评审会上逐条过，每条只需回答「A 还是 B」，并当场记录结论与责任人。
> 未确认的条目对应的 Epic **不允许进入排期承诺**（见 10 文档的 L3 规则）。

## 使用说明

每条包含：问题、为什么重要、可能的答案分支、每个分支导致的排期后果、确认方式、结论栏。
标 ⭐ 的三条（#1、#4、#6）是排期的决定性变量，必须在阶段 0 结束前有结论。

---

## ⭐ #1 UCDM「更新回切」能否支持临时沙盒的变更回切？

- **影响**：E6（冲突检测与合并回切）
- **为什么重要**：现有回切的应用场景是整库级容灾主备切换，与「只合并一部分变更」在颗粒度上有本质差距。如果需要走不同代码路径，E6 的性质从「扩展复用」变成「接近全新开发」。
- **确认方式**：让熟悉回切模块的研发当场说明触发条件、数据量假设、是否依赖「两库同构且长期同步」这一前提。

| 分支 | 排期后果 |
| --- | --- |
| A：可复用同一代码路径，仅需参数化 | E6 维持 8-15 人天，定性为「扩展复用」 |
| B：需要新的代码路径 | E6 上调至 20-35 人天，且必须先做设计评审，不能直接排期 |
| C：现有回切依赖长期同步前提，短生命周期沙盒不成立 | 方案需要重新设计合并路径，**阶段 2 不能启动** |

**结论**：＿＿＿＿＿　**责任人**：＿＿＿＿＿　**确认日期**：＿＿＿＿＿

## #2 现有 Celery Worker 的并发配置与队列积压策略是什么？

- **影响**：E7（配额与治理）、E9（并发压测）
- **为什么重要**：这是一个能快速拿到确定答案的标准配置问题，但它决定了「数百个短生命周期沙盒」是否需要架构级改动。

| 分支 | 排期后果 |
| --- | --- |
| A：现有配置可容纳，仅需新增队列 | E7 维持 8-10 人天 |
| B：需要新增独立 Worker 组与调度改造 | E7 上调，并新增部署与运维文档工作量 |
| C：Airflow 元数据库会成为瓶颈（reaper 每分钟触发） | 需先做元数据保留期治理，列为阶段 1 前置任务 |

**结论**：＿＿＿＿＿

## #3 容灾库快照间隔（默认约 10 分钟）能否为沙盒场景调短？成本增量多少？

- **影响**：9.1 节的性能承诺、E1
- **为什么重要**：快照间隔是 `near_current` 模式下数据新鲜度的上限，直接决定对客户能承诺什么。

| 分支 | 排期后果 |
| --- | --- |
| A：可调短且成本可接受 | `near_current` 新鲜度承诺可收紧，卖点更强 |
| B：不可调或成本高 | 对外新鲜度承诺必须写明「最多落后一个快照间隔」，写入 SLA 文案 |

**结论**：＿＿＿＿＿（需附成本测算数字）

## ⭐ #4 「标记/回滚」是否仅支持 Oracle？MySQL 有无等价能力？

- **影响**：E11 是否成立、P0 数据库排期、阶段 1 选哪个库做原型
- **为什么重要**：这直接决定阶段 1 的原型选 Oracle 还是 MySQL。

| 分支 | 排期后果 |
| --- | --- |
| A：MySQL 已有等价能力 | E11 = 0，阶段 1 可选 MySQL（spike 成本更低） |
| B：MySQL 缺失 | E11 = 8-12 人天；阶段 1 改用 Oracle 做原型；或首版用「按时间点重建沙盒」替代「回滚到检查点」作为降级方案 |

**降级方案说明**：若选 B 的降级路径，MCP 工具与 API 契约无需改动，只是回滚耗时从秒级变成分钟级，需在文档中明示。

**结论**：＿＿＿＿＿

## #5 临时账号的 CDB/非 CDB 差异化创建逻辑是否已封装为内部 API？

- **影响**：E3（REST API 与鉴权）、E5（审批 UI）
- **为什么重要**：若每次都要手写 SQL 拼接，则临时凭据的创建/销毁存在注入与残留风险，需要额外的封装与测试工作量。

| 分支 | 排期后果 |
| --- | --- |
| A：已封装 | E3 维持估算 |
| B：未封装 | E3 增加 3-5 人天用于封装与安全测试，且必须做 SQL 注入防护评审 |

**结论**：＿＿＿＿＿

## ⭐ #6 ChangeSet 走块级差异翻译还是逻辑日志解析？RBA 现有日志解析能否复用？

- **影响**：E2，**可能是全表中偏差最大的一项**
- **为什么重要**：RBA 已经在做「实时日志流获取 + 增量备份合成」，如果它已经解析到逻辑变更层面，路径 B 的成本会大幅下降；如果只到物理日志块层面，则两条路径都需要新开发。
- **确认方式**：不靠口头判断，按 [02 文档](02-spike-ab-plan.md) 做时间盒 spike，用 `compare_changesets.py` 出证据。

| 分支 | 排期后果 |
| --- | --- |
| A：RBA 已有可复用的逻辑变更解析 | E2 下调，定性 L1/L2 |
| B：需在沙盒库新开日志解析 | E2 维持 10-16 人天，定性 L2 |
| C：只能走块级翻译，且需按库分别实现 | E2 上调至 30-60 人天（数倍偏差），首版应收窄到单一数据库 |

**结论**：＿＿＿＿＿

## #7 「整变更集全量合并 + 时间戳冲突检测」在真实客户场景够用吗？

- **影响**：E6 范围、POC 验收标准
- **为什么重要**：这是需求问题不是技术问题，必须在 POC 前与 1-2 家目标客户确认审批颗粒度诉求。

| 分支 | 排期后果 |
| --- | --- |
| A：够用 | 首版策略不变，保持保守 |
| B：客户要求按表/按行选择性合并 | 需引入行级版本号，E6 大幅上调；建议仍在首版保持全量合并，把选择性合并列入路线图第二版 |

**结论**：＿＿＿＿＿（须附客户访谈记录编号）

## #8 客户为什么不直接用 Neon/Supabase/Postgres.ai？

- **影响**：对外话术与目标客户画像（非工程）
- **标准答案（需销售/产品共识）**：因为客户的核心数据在 Oracle/DB2/SQL Server/信创库里，
  这些产品**只能作用于跑在它们自己引擎上的数据**；一牧的价值是「存量异构库 + 不改造源端 + 私有化/信创 + 审批合规闭环」，而不是机制本身更先进。
- **配套动作**：按 [07 文档](07-benchmark-suite.md) 第 4 节做横向对比，用同一套负载跑出可比数字，落后项如实呈现。

**结论**：＿＿＿＿＿
