一、执行摘要
本报告回答三个问题：为什么要做「Agent 可写沙盒 + 合并回切」这个机制；这个机制在当前全球市场里值多少、处于什么位置；以及技术上具体怎么做、要投入多少。
•	核心判断一：AI Agent 要真正产生价值，必须能操作数据库，但企业不敢让 Agent 直碰生产库——这是一个正在快速扩大、目前无解的信任缺口，「可写沙盒+合并回切」是目前能想到的最直接的解法；
•	核心判断二（已修正）：我们最初只研究了 Delphix、Actifio（Google）、Rubrik、Cohesity、Tonic.ai/K2view 五家 CDM/TDM 赛道公司，据此得出「全行业没有人做可写沙盒」的结论。补充调研 AI 原生数据库赛道后，这个结论必须收窄：以 Neon、Supabase、PlanetScale、Dolt、Databricks/Snowflake 为代表的一批云原生/AI 原生数据库，已经把「零拷贝分支 + Agent 可写 + 差异对比 + 合并回主干」做成了产品甚至默认能力，并普遍通过 MCP 直接开放给 Agent 调用。真正的空白不是「可写沙盒」这个机制本身，而是「把这套机制套用到企业存量的、非云原生的生产库（Oracle / DB2 / SQL Server / 达梦 / Kingbase）之上，且不改造源端」——这一点在第四之二、四之四部分详述；
•	核心判断三：一牧的差异化必须重新表述为「存量异构生产库 + 私有化 + 信创 + Agent 可写分支」这个组合，而不是「机制首创」。在这个收窄后的定义下，窗口期判断（12-18 个月）依然成立，但论证依据从「无人在做」变成「做的人在另一个技术栈上，短期内跨不过来」。
这份报告不建议以「全面赶超 Delphix/Rubrik/Cohesity」为目标——那是资源量级不对等的仗。真正值得投入的，是抓住「存量异构生产库上的 Agent 可写分支」这个尚未被云原生阵营覆盖、也未被 CDM 阵营做出闭环的交叉地带。同时，第十八部分给出了本次修订暴露出的方法论问题及改进建议——本报告第一版之所以给出过强的结论，根因是竞品调研的范围界定方法有缺陷，这个问题比结论本身更值得修复。
 
二、背景与问题：Agent 时代的数据信任缺口
企业内部正在规模化部署 AI Agent（自动化测试、自动化运维、数据分析类），这些 Agent 要产生真实价值，必须能够读写数据库，而不只是读取文档或摘要。但企业不可能把 Agent 直接接入生产库——一旦 Agent 因模型幻觉生成错误 SQL 并执行，后果不可逆，这是任何企业安全团队都无法接受的风险。
这个矛盾目前没有成熟的行业解法：企业要么完全不让 Agent 碰数据库（严重限制 Agent 的实际价值），要么冒险开放有限权限（埋下事故隐患）。这就是本报告要论证的核心机会所在。
 
三、为什么要做「Agent 可写沙盒 + 合并回切」
3.1 「只读」为什么不够
行业目前的主流方案（见第四部分详述）是给 Agent「只读」访问权限——让 Agent 能查、能搜、能发现有哪些数据、状态如何。这类方案能解决「Agent 找不到数据」的问题，但解决不了「Agent 需要真正操作数据才能完成任务」的问题：自动化测试 Agent 需要往数据库里写测试数据、跑变更脚本；自动化运维 Agent 需要执行修复性的数据操作；数据分析 Agent 有时需要临时建表、跑中间计算——这些都是「只读」权限做不到的场景。
3.2 「可写沙盒 + 合并回切」的逻辑闭环
这个机制的设计逻辑很直接：给 Agent 一个「任意时间点、可读写、用完即焚、完全不影响生产」的数据库分支（沙盒）；Agent 在这个分支里可以放心操作、放心试错，因为底层是零拷贝虚拟克隆，出错的代价趋近于零；操作完成后，变更以结构化差异形式呈现给人工审核；审核通过则合并回生产，不通过则直接丢弃。
这相当于给数据库操作装上了 Git 式的分支/合并/回滚机制——这正是软件工程过去十几年里解决「多人协作、放心试错、可控合并」问题最成熟的范式，本质是把这个范式从代码搬到数据。
3.3 为什么这个机制现在必须做，而不是可以再等等
•	AI Agent 在企业内部的部署速度远超预期，「Agent 想操作数据、企业不敢给权限」这个矛盾正在越来越多的客户对话里出现，不是假设性需求；
•	现有的「只读」方案能满足的场景有限，客户很快会问「能不能让 Agent 真的帮我把这件事做了」，这是下一步必然会被问到的问题；
•	第四部分的研究证实，在「企业存量异构生产库」这个战场上，还没有公司把这个能力做成熟并 GA；而第四之二部分同时证实，云原生数据库阵营已经把这套范式验证过了——这意味着机制本身的可行性风险很低，但也意味着「教育市场」的窗口比原先估计的更短：客户很可能是先在 Neon/Supabase 这类产品上体验过数据库分支，再回头要求一牧在 Oracle 上给出同样的体验。

四之二、竞争格局（二）：AI 原生数据库与云数据库「分支」技术现状
第一版报告的最大缺口，是把竞品范围限定在了「和一牧做同一件事的公司」，而没有覆盖「用完全不同的技术路径解决同一个客户问题的公司」。对「Agent 需要一个可写、可试错、可丢弃的数据库」这个需求而言，真正已经跑通产品化闭环的，恰恰是 AI 原生/云原生数据库这一批玩家。

4.2.2 从这张表能得出的四个判断
•	判断一：「Agent 可写数据库分支」不是空白，而是已被验证的范式。 Neon 明确把「给每个 AI Agent 任务开一个数据库分支」作为主要场景对外宣传，Supabase/PlanetScale 把分支与 PR 流程绑定，Dolt 甚至把 Git 语义做进了存储引擎。第一版报告「全行业尚无人做」的表述在事实层面站不住脚，必须修正。
•	判断二：这些玩家全部集中在「云原生、开源系、新建库」这一侧。 它们的分支能力依赖于自有存储引擎（Neon 的存算分离页服务、Dolt 的 Merkle DAG、Delta/Iceberg 的多版本表格式），因此天然只能作用于「跑在它们自己引擎上的数据」。企业里那些跑在 Oracle RAC、DB2、SQL Server、达梦上的核心业务库，它们一个都碰不到。
•	判断三：真正难的部分不是「分支」，是「合并回生产」。 值得注意的是，上表中做得最好的几家，合并能力也主要停留在 schema 层（PlanetScale、Supabase）或表级替换（Snowflake），只有 Dolt 做到了行级三方合并，而 Dolt 的代价是重写了整个存储引擎。这反向印证了本方案第 9.3 节「首版采用整变更集全量合并、不做部分回切」的保守策略是正确的，而不是能力不足的妥协。
•	判断四：一牧的「差异翻译层」不应闭门造车。 第八部分把 ChangeSet 差异翻译层定为「唯一的核心新增算法模块」，而 Dolt 的行级 diff/merge 语义、Delta Lake 的 Change Data Feed、以及各数据库自身的逻辑日志（Oracle LogMiner、MySQL binlog、PostgreSQL 逻辑解码）都提供了成熟的语义参考甚至可直接复用的能力。建议在设计阶段先做一轮「块级差异 vs 逻辑日志解析」的技术路线对比，而不是默认走块级翻译。

4.2.3 对本方案技术选型的直接影响
现有方案基于「块级快照差异 → 翻译成表/行级摘要」。引入上述参照物后，至少有两条替代路径需要在预研阶段一并评估：
路径	实现方式	优点	风险
A（现方案）块级差异翻译	读取 COW 快照的块级变化，反查数据文件结构还原到表/行	不依赖数据库自身日志能力，跨库统一	块到行的还原依赖各数据库物理存储格式，Oracle 与 MySQL 需分别实现，工作量可能被低估
B 逻辑日志解析	在沙盒库上开启逻辑日志（LogMiner/binlog/逻辑复制槽），直接得到行级变更	语义天然是行级，与「合并回生产」所需的操作序列一一对应；各数据库均有成熟工具链	需要在沙盒库上额外开启日志，有性能与容量开销
C 影子表/触发器	在沙盒库内对目标表挂变更记录	实现简单，颗粒度精确	侵入沙盒库结构，Agent 的 DDL 操作会破坏它，仅适合窄场景
建议：把「A vs B 的对比验证」列为技术预研阶段的必做项，其结论会显著影响 E2 的工作量（现估 10-16 人天，若 A 路径需按数据库分别实现物理格式解析，存在数倍偏差的可能）。

把三类竞争者放在同一张图上，用两个维度切分：横轴是「数据库形态」（云原生新建库 ↔ 企业存量异构生产库），纵轴是「Agent 能力深度」（只读发现 ↔ 可写并合并回生产）。

存量异构库 + 可写合并	暂无成熟商用产品	一牧的目标象限

一牧真正应当对外主张的判断，是这一句而不是「全行业空白」：
「Agent 可写数据库分支」这个范式已经被云原生数据库验证有效并进入商用，但它今天只能作用于新建的云原生库；企业 80% 的核心数据仍在 Oracle/DB2/SQL Server/信创库里，这部分数据的 Agent 可写分支能力，目前没有成熟的商用产品——一牧的机会在这里。
这个表述的好处是：它可被证伪、可被验证、经得起客户和投资人的追问，而且不会在客户提到 Neon 时让一牧陷入被动。
 
五、市场价值评估
5.1 这个空白为什么值钱：三个信号
•	资本信号：Delphix 年营收区间约 1-2.5 亿美元，Rubrik 作为上市公司市值数十亿美元，这两家公司过去两年都在往「AI 驱动数据管理」方向加大投入，说明资本市场认可这个方向的长期价值，愿意为「数据+AI」的故事持续买单；
•	产品信号：Rubrik 2026年6月的表态是「Today Rubrik becomes an agent」，把整个公司定位重新押注在 agentic 方向，Cohesity/Delphix 也在同一时间窗口密集发布 MCP 相关能力——三家头部公司几乎同步在 2026 年上半年集中发力，说明这是一个公认的下一战场，不是小众方向；
•	需求信号：Perforce 官方数据显示，测试团队获取一份新鲜数据平均要等待超过 1 天，42% 要等数周到数月——这是「数据供给效率」这个老问题在 AI Agent 时代被重新放大：过去人工可以忍受的等待，Agent 场景下会变成明显的效率瓶颈，需求侧的紧迫性在提高。

5.2 一牧的独特卡位：三个条件的交叉点
「可写沙盒+合并回切」单独拿出来看，不足以构成护城河——第四之二部分已经证明这个机制在云原生数据库上早已产品化。真正值钱的，是把这个机制和一牧已经拥有的另外两个条件叠加在一起：
条件	一牧现状	海外头部公司现状	AI 原生数据库厂商现状
结构化数据库虚拟化引擎（面向存量异构库）	已有多年积累（RBA/UCDM），信创数据库、Exadata 兼容等硬骨头已经啃过	Delphix 有类似引擎但不做中国市场；Rubrik/Cohesity 聚焦非结构化数据，结构化数据库能力较弱	完全不具备，其分支能力绑定在自有存储引擎上，无法作用于外部生产库
Agent 可写沙盒 + 合并回切	技术方案已完成评审级细节设计，尚未产品化	全部停留在只读发现层	已产品化（Neon/Supabase/PlanetScale/Dolt），且合并语义比一牧首版方案更成熟
中国信创市场准入	核心优势区，本土私有化部署，符合数据不出域要求	基本空白，APAC 布局集中在新加坡、日本，无中国大陆布局	基本空白，但本土云厂商（PolarDB/GaussDB/OceanBase）在此有主场优势

修正后的结论：一牧不是「唯一同时具备三个条件的公司」这种无法验证的表述，而是「在存量异构生产库这个象限里，目前没有看到已 GA 的可写沙盒商用产品」。价值来源于象限的空缺，而非机制的独创性；相应地，护城河也不是机制，而是 RBA/UCDM 对异构与信创数据库多年积累的兼容性工程量。

5.3 时效性判断：窗口期大约有多长
这个窗口不是无限的，且威胁来自两个方向而不是一个：
•	同赛道方向：Delphix 已经把「测试数据/环境的 Agent 化供给」写进公开路线图，说明工程投入方向已经确定；Rubrik、Cohesity 的资金和渠道能力远超一牧，一旦决定跟进「可写沙盒」这个具体机制，追赶速度会很快；
•	跨赛道方向（第一版遗漏）：Neon 被 Databricks 收购后，「数据库分支」正在成为数据平台的标配特性；Postgres.ai 这类开源实现进一步降低了 PostgreSQL 场景的替代门槛。对于客户新建的、跑在开源库上的系统，一牧很可能根本没有机会参与竞争——这会持续压缩一牧的可服务市场（SAM），使窗口期的实质缩短。
综合两个方向，我们维持 12-18 个月的窗口期判断，但把它的含义改为：一牧需要在 12-18 个月内，在存量异构生产库场景里跑出可复制的标杆案例，而不是「抢在别人之前发明这个机制」。
 
六、核心设计理念：不是新系统，是现有流水线的第四个出口
《数据库云化管理平台白皮书》4.2.2 节披露的测试流程拓扑图显示，DCM 现有架构已经是三段式流水线：数据准备阶段 → 数据处理阶段 → 数据交付阶段。其中「数据处理阶段」由任务编排层（经与《使用手册》交叉验证，确认底层是 Apache Airflow + Celery 标准组合）执行「快速克隆/时间戳」+「数据库挂载」+「一致性验证」，产出物交付给三类现有目标：应急数据库、开发数据库、数据分析。
关键判断：Agent 沙盒 = 在「数据交付阶段」新增第四类交付目标（Agent 沙盒库），复用完全相同的流水线，只是交付对象从「人/应用」变成「Agent」，并在交付后新增一段「审批合并回切」逻辑。
这个判断直接改写了工作量结构——不需要重新设计克隆、挂载、一致性校验这些能力，只需要在任务编排层新增一类任务，并在其之上叠加审批工作流。
 
七、与 DCM 现有架构的映射关系

7.2 设计红线（必须遵守）
《产品与方案优势说明》明确指出，一牧 DCM 相对其他 CDM 产品的核心优势之一，是源端捕获采用标准数据库备份接口（无 iSCSI/NFS 挂载源端），从而避免了「需要 mount/umount 超级权限」「频繁导致源端服务器崩溃」等其他产品存在的高侵入性风险。
设计红线：Agent 沙盒的任何新增能力，不得在源端引入新的挂载、新的权限要求或新的 Agent 部署。所有编排、审批、差异翻译、临时凭据生成，都必须封装在「目标端挂载 + 任务编排层」，与源端「标准接口无代理捕获」完全解耦。这是一牧的核心技术优势所在，不能因为做 Agent 沙盒而牺牲。

九、核心机制设计
9.1 沙盒创建：区分「近实时」与「任意历史点」两种模式
《产品与方案优势说明》披露了一个关键机制：副本挂载分两个阶段——(A) 找最近的快照点，速度快；(B) 把日志加载到目标时间点，耗时与日志量成正比（经验值：加载 N 小时日志约需 N/2 小时）。一牧通过维护一个持续应用日志的容灾库，并对其定期打快照（默认约 10 分钟一次），让「接近当前时间」的请求可以直接命中最近快照，避免走 (B) 阶段。
这意味着 Agent 沙盒不能承诺统一的创建 SLA。API 设计需要新增 timing_mode 参数，区分 near_current（复用最近快照，分钟级）与 point_in_time（可能需要日志回放，耗时随时间跨度增长，需要异步轮询）。

9.2 检查点与丢弃：直接复用「标记/回滚」
使用手册 4.1.2 节记录的「标记」+「标记时间点回滚」功能，与 Agent 沙盒需要的「检查点」和「丢弃变更」语义高度一致，且已经过生产验证。此前假设需要「全新开发变更捕获引擎」，现在看，底层的捕获与回滚机制已经现成可用，唯一需要新增开发的，是把这些机制之上的差异结果翻译成 Agent 能理解的表/行级摘要。

9.3 合并回生产：复用 UCDM 更新回切，首版采用保守策略
《产品与方案优势说明》确认「容灾回切功能」已在 Oracle、DB2、MySQL 上生产验证，进一步印证 UCDM 更新回切机制是成熟能力。但该能力目前的应用场景是整库级别的容灾主备切换，与 Agent 沙盒需要的「只合并一部分变更」在颗粒度上仍有差距。
•	首版建议：不做「部分回切」，审批粒度是整个变更集——要么全部合并，要么全部丢弃，避免「选择性回切」这个复杂功能在首版就要开发；
•	冲突检测采用简单时间戳比对：回切前检查生产库对应表的最后变更时间是否晚于沙盒基准时间点，如果是则拒绝回切，要求基于最新时间点重新创建沙盒。

9.4 临时凭据设计：复用现有权限管理模式
使用手册披露的 Oracle CDB/非 CDB 环境权限配置，是一牧现有系统里创建数据库账号的标准模式。Agent 沙盒的临时凭据应复用同一套机制，只是把权限范围从「只读监控视图」扩展为「沙盒库范围内的读写权限」，账号随沙盒销毁自动 drop user，不允许长期存活。
 
十、API 与接口设计
10.1 REST API
核心接口沿用「创建-查询-检查点-提交审批-审批-回切-销毁」的资源模型，关键字段对齐使用手册中已验证的真实字段名，并新增两个沙盒场景特有字段：
新增字段	说明	设计理由
timing_mode	near_current（近实时）或 point_in_time（任意历史点）	对应 9.1 节的双路径性能模型，避免统一 SLA 承诺失真
mount_profile	轻量化参数模板，而非默认沿用源端参数	沙盒不需要生产级别的资源配置，避免不必要的资源占用
ttl_seconds	强制必填，不允许沿用「默认永久保留」的习惯	防止沙盒资源泄漏，这是沙盒场景与现有挂载场景的关键差异

10.2 MCP 工具接口（供 Agent / LLM 工作流直接调用）
建议封装为 4 个标准 MCP 工具：request_data_sandbox（申请沙盒）、get_sandbox_diff（获取变更摘要）、submit_sandbox_for_review（提交审批）、discard_sandbox（丢弃）。这一层不涉及底层引擎改动，属于独立的封装工作，可以和底层能力并行开发。

12.2 高频小颗粒度场景的压力预估
现有基线数据反映的场景是「少量大型副本」。Agent 沙盒的目标场景是同时存在数十到数百个短生命周期的小颗粒度沙盒，这与现有基线场景有本质差异。经确认底层任务编排是标准的 Airflow + Celery 组件后，需要向研发团队确认现有 Celery Worker 并发配置是否已支持这个规模，这是一个可以快速拿到确定答案的标准配置问题。

十八、方法论改进建议：一牧接下来更科学的做事方式
本次修订暴露出的问题不只是「漏了几家竞品」，而是产出这类判断的方法本身存在系统性缺陷。以下建议按「先修方法、再修结论」的顺序给出。

18.1 竞品调研：从「找同行」改为「找替代方案」
第一版报告的根因错误，是把竞品定义为「和我们做同一件事的公司」，而客户的定义是「能解决我同一个问题的任何东西」。改进做法：
•	以问题而非赛道界定范围：先写清楚要研究的客户问题（「让 Agent 安全地对数据库做写操作」），再穷举所有可能的解法路径（CDM 克隆、云数据库分支、版本化数据库、数仓零拷贝克隆、合成数据、只读+人工执行、干脆不用 Agent），每条路径至少找 2 个代表玩家；
•	强制包含「非竞品替代品」：包括开源方案（Postgres.ai、Dolt）和「客户自己拿 ZFS/LVM 快照攒一套」的土办法，后者往往是最真实的竞争对手；
•	每条竞品结论必须可溯源：标注信息来源链接、检索日期、以及该结论是「厂商官宣」「第三方报道」还是「我们的推断」，三者不能混写；
•	设定复核节奏：AI 相关能力按季度复核一次，形成竞品情报台账（表格即可，不需要系统），而不是每次写报告临时查一遍；
•	主动寻找证伪证据：每写下一条「没有人做过 X」，必须先花时间尝试推翻它，把尝试过的检索路径记录下来。第一版如果做过这一步，不会出现「全行业空白」的表述。

18.2 结论表述：只写可证伪、可验证的判断
建议在本报告及后续对外材料中执行三条硬规则：
•	禁止使用「唯一」「全球首创」「全行业空白」这类无法验证且一旦被证伪代价极高的表述，改为带限定条件的表述（限定象限、限定数据库类型、限定部署形态）；
•	所有数字必须带来源和口径：例如「测试团队获取数据平均等待 1 天以上、42% 等待数周至数月」这类引用，需注明调研主体、样本量、调研年份，否则在客户和投资人面前不具备说服力；
•	区分事实、推断与假设：报告中每个关键判断前置标注属于哪一类，评审时只需重点讨论「推断」和「假设」两类。

18.3 工作量估算：从单点区间改为带依据分级的三点估计
•	对每个 Epic 标注估算依据等级：L1（有可直接参照的既有代码）、L2（技术路线明确但需新写）、L3（技术路线未定），L3 项不允许进入排期承诺，只能进入预研；
•	对 L2/L3 项给出乐观/最可能/悲观三点估计，而不是一个区间；
•	把「技术路线未定」的部分（如 4.2.3 的 A/B/C 路径）拆成独立的 spike 任务，用固定时间盒（例如 5 人天）先收敛路线，再估工作量。

18.4 需求验证：先证明客户会买，再证明技术能做
现有报告的技术论证密度远高于需求论证密度，这是典型的技术驱动型偏差。建议在启动 E1-E9 之前，先补一轮结构化的客户访谈：
•	访谈对象：5-8 家现有 DCM 客户的测试负责人/DBA/安全负责人，覆盖金融、运营商、政企三类；
•	访谈目标（回答具体问题而非收集泛泛好评）：他们内部是否已经在跑数据库相关的 Agent？现在怎么解决权限问题？变更审批目前由谁签字、平均耗时多久？如果有可写沙盒，愿意为它单独付费还是期望包含在现有 DCM 里？
•	验收标准：只有当至少 3 家客户能明确说出具体的 Agent 使用场景和当前的替代做法时，才认为需求被验证；否则应把项目降级为技术预研而非产品立项。

18.5 POC 设计：预先定义可量化的成功判据
建议在生产级 POC 启动前就把验收指标写死，避免事后用「客户觉得不错」来结题。参考指标集：
维度	指标	建议目标值（需与客户共同确认）
效率	沙盒创建耗时（near_current / point_in_time 分别统计）	near_current P95 < 5 分钟
效率	Agent 任务从「提出数据需求」到「拿到可写环境」的端到端耗时，与现有人工流程对比	降幅 ≥ 80%
规模	单集群并发存活沙盒数量上限（压测得出）	≥ 100
准确性	ChangeSet 差异摘要与实际变更的一致率（人工抽样核对）	100%（差异漏报是不可接受的安全问题）
安全	源端新增权限/挂载/代理数量	必须为 0（对应第七部分设计红线）
成本	单个沙盒的平均存储增量与生命周期成本	与全量克隆方案对比给出倍数
可靠	合并回切成功率、回滚成功率、失败时生产库受影响次数	受影响次数必须为 0

18.6 建立可复现的基准测试，而不是引用零散实测值
第十二部分的性能基线来自白皮书的零散实测，场景与 Agent 沙盒差异很大。建议搭建一套固定的基准测试脚本（数据集规模、并发模型、操作序列固定），每次版本迭代跑一次，形成可纵向对比的曲线；同时把 Neon/Postgres.ai 这类可公开获取的产品纳入横向对比，用同一套负载跑出可比数字——这比任何竞品分析文字都更有说服力。

建议为本项目维护一份简单的风险台账，至少包含以下几条，并为每条指定负责人、验证方式和触发应对的阈值：
风险	说明	建议的验证/应对方式

十九之二、对交付物的第二轮批判性复核（重要）

上述交付物已经过一次针对自身的批判性复核并整体修订。复核结论是：第一版交付物**在工程完备性上做得过头，在前提正确性上做得不足**——把精力花在 schema、状态机、校验脚本这些看起来扎实的东西上，却没有先质疑几个会让整个方案不成立的前提。查出三个致命矛盾：

1. **脱敏默认开启 与 合并回生产互斥**。沙盒里是脱敏后的假数据，其变更合并回生产等于数据污染，定位列被脱敏还会导致 WHERE 失配。首版据此改为「**变更导出**」：沙盒产出经审核的变更集，由客户既有变更流程执行，一牧**不写客户的生产库**。这同时消解了另外三个问题（语义之争、冲突检测不可用、DDL 组合死锁），并使对应 Epic 的风险等级由 L3 降为 L2。
2. **块级差异与逻辑日志的语义类型不同**。前者是净状态差，后者是操作序列，二者对同一组操作在定义上不可能等价；第一版却把「两条路径表示必须相同」写成了 spike 的通过判据，等于把实验设计成必然失败。现已把 ChangeSet 的规范形式唯一确定为**净状态差**，位点信息降级为溯源字段。
3. **数据通路带宽与目标场景差 1-2 个数量级**。本报告实测 DCM↔挂载端约 20 MB/s，而「100 并发沙盒」的需求约 1 GB/s。第一版只把它写成「建议同机房部署」。现已将**数据通路实测**列为阶段 0 的第三个出口判据，并规定所有 SLA 目标必须由实测反推。

同时修正了五处不严谨与四处方法论缺陷，其中较重要的是：删除「差异一致率 = 100%」这类抽样无法证明的指标（改为 fixture 全集零失配 + 失配率置信上界）；工作量合计改用蒙特卡洛给 P10/P50/P90（简单相加乐观值与悲观值犯了 PERT 求和谬误）；块级差异路径不再给估算而是直接标注「首版范围外」；表级时间戳冲突检测改为行级乐观并发控制；以及把校验脚本的自我描述从「全部自测通过」降级为「**契约自洽性检查，不构成对系统行为的任何验证**」。

全部未显式记录的前提，已收敛为一份[假设清单](docs/agent-sandbox/00-assumptions.md)，逐条标注「事实/推断/假设」、若不成立的后果与验证方式——上述三个致命矛盾，全部是这张表能提前拦住的。

该前置决策已于 2026-09-07 落定：**首版为「变更导出」**——沙盒可写、用完即焚、产出经审核的变更集，由客户既有变更流程执行，一牧的产品不写客户的生产库；脱敏随之升为不可关闭的合规红线，「不脱敏 + 直接合并」移出首版范围。相应地，E6 由 L3 降为 L2，红线指标「非预期生产库写入 = 0」因预期写入为空集而变为可严格判定。

注意：这些仍是设计稿，尚未经内部代码校验。进入阶段一之前须完成**三项并行的出口判据**（A/B spike、客户访谈、数据通路实测）——这三条与上述产品决策相互独立，不因决策落定而豁免。
